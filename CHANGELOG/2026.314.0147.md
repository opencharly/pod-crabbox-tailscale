# 2026.314.0147 — fix: this image now starts its daemon on the venue it declares

The image now **starts its daemon** on the venue it declares — and the gate now proves the daemon starts, rather than that a file exists.

## Summary

Until this change, `tailscaled.service` was *"enabled"* — a link in `multi-user.target.wants` plus a drop-in. That is a filesystem fact; it becomes a runtime fact only when systemd is PID 1, and this image declares PID 1 as the base's `sshd -D` (`charly.yml:50`, its own words). So on the venue it declares, nothing followed the link and `tailscaled` never started. A consumer expecting a mesh on such a lease had no daemon to join with — the whole point of the image (`opencharly/pod-crabbox-tailscale#2`).

**The base offers no extension point**, and this is measured rather than asserted — on `main`, before this branch:

```console
$ git grep -nE "systemctl|service:|start:|supervisor|entrypoint" main -- "*.yml" "*.sh"
$ echo "matches: $(git grep -cE "systemctl|service:|start:|supervisor|entrypoint" main -- "*.yml" "*.sh" | wc -l)"
matches: 0
```

Zero — the repo had no start step of any kind. Reading the base repo settles the rest: `candy/crabbox-guest/bootstrap.sh` is 36 lines that apply inputs and return (no `exec`, no hook directory), and the direct-mode entrypoint is the base's own `exec sshd -D`. So the fix belongs here, where the delta is owned:

- **`candy/tailscale-lease/tailscale-init.sh`** — this variant's direct-mode entrypoint: exports `TS_DEBUG_DISABLE_UDP_GSO=1` into the **daemon's own** environment (the drop-in only reaches a unit systemd starts), starts `tailscaled` with explicit state and socket paths, then `exec`s the base `/usr/local/bin/crabbox-lease-init` **unchanged** — the inherited `/crabbox` contract (inputs, sshd on 2222, readiness hook) is exactly what the base provides.
- **`entrypoint:` on the box** names it. That declaration is the fix: without it the script ships and is never run.
- **One shared starter**, `tailscaled-start.sh`, run by BOTH the entrypoint and the check, so the proven command and the shipped command cannot drift; **two checks**: `tailscale-daemon-starts` runs that file and fails if the daemon exits or its socket never appears, and `tailscale-entrypoint` asserts the entrypoint delegates to the starter and execs the base init.
- **Description corrected** — enablement no longer reads as though the daemon runs; the drop-in stays, for a venue that runs systemd as PID 1.

`0 skipped` is quoted deliberately: a skipped step reads as a satisfied one, so the count is part of the evidence.

**The negative arm.** `tailscale-daemon-starts` runs `/usr/bin/tailscaled` directly, so on any tree without the package its first line fails and the step cannot pass — the check cannot be satisfied by the file's mere presence, which is exactly what round 1 objected to.

**Round-2 RCA — the missed control, named.** My pre-push gate proved a command I had **written in the check**, not the command the image ships: the check ran `tailscaled --tun=userspace-networking` with `/tmp` paths while the entrypoint ran plain `tailscaled` with `/var/lib/tailscale` and `/run/tailscale`. The shipped invocation was executed by no gate, the check's own description was false, and — the part I missed — on a TUN-less lease the entrypoint's plain `tailscaled` would fail to start, which is the very bug this PR fixes. **The control:** a gate step must EXECUTE the shipped artifact, and where two places need the same behaviour they share one file so they cannot diverge. That is the shape now: `tailscaled-start.sh` is run by both the entrypoint and the check, and `--tun=userspace-networking` is in it because a lease container has no `/dev/net/tun` unless its consumer attaches one.

**Tier: `analysed on a live system`, not `fully tested and validated`.** The daemon start now runs live inside the check container, but two things the gate does **not** execute: the entrypoint's handover to `crabbox-lease-init`, and the behaviour on a booted lease. Those are deployment-context facts. Claiming the top tier for a path the gate never runs is precisely the inflation the round-1 review named, so the tier says what ran.

**What remains open, and it is only the credential-bearing half.** `#2` stays open for the deployment bed, whose PRESENCE step asserts the daemon is running with `TS_DEBUG_DISABLE_UDP_GSO=1` in its environment, with the base image as the ABSENCE control and the **tailnet join** a visible skip — the join needs a container auth key this host does not hold (`TS_AUTHKEY` unset, no secrets store reachable non-interactively). The daemon start needs no credential, which is why it is proven here instead of deferred.
